# Fieldwork runbooks

These are **consultant-designed test procedures**. Microsoft references identify the relevant product behavior; they do not imply Microsoft mandates these exact experiments. Use approved test identities, destinations and synthetic content. No test below was executed against a real tenant during authoring. Pair results with the [control catalog](../controls/CONTROL-CATALOG.md) and the [test worksheet](../templates/test-record.csv).

## Common test record

Record requirement, control IDs, tenant/cloud, feature/license, authorization, expected outcome, identity/resource/client, preconditions, UTC start/end, observed result, evidence IDs, interpretation, limitation, cleanup and reviewer. Separate passive evidence review from sign-ins, messages, policy changes, restores and tool actions. This is **consultant method** for interpreting Microsoft's scoped authorization and event evidence. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search)

Pre-register the observation that would disprove the control claim. A negative test is meaningful only if a positive control establishes that the test identity, client and resource work as intended. If the environment or permissions prevent the test, record Not assessed. **Consultant method**, particularly relevant to report-only policies, DLP simulation and workload-specific permissions. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)

## T01 — Effective authentication and access

**Claim to test:** the adopted identity population receives the required access controls. Microsoft distinguishes policy evaluation from enforcement, and service principals cannot satisfy human MFA. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S10: Conditional Access for workload identities](https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity)

1. Export all policy states, assignments, conditions, grant/session controls and exclusions. Record the security-defaults alternative where used. Build cases for administrators, ordinary staff, guests and exceptions. [S55: Graph: List Conditional Access policies](https://learn.microsoft.com/en-us/graph/api/conditionalaccessroot-list-policies?view=graph-rest-1.0); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview); [S63: Security defaults in Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/fundamentals/security-defaults)
2. Select a test resource/client combination per case. Include trusted/untrusted location and managed/unmanaged device cases when material. Record existing authentication claims; absence of an interactive MFA prompt does not alone prove bypass. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)
3. In an authorized fresh session, perform an allowed attempt and a case that should fail the adopted requirement. Record correlation identifiers and actual sign-in authentication/Conditional Access details. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)
4. Resolve how multiple policies and accepted guest claims affected the result. Treat What If or report-only output as design evidence and corroborate operation separately. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S16: Cross-tenant access overview](https://learn.microsoft.com/en-us/entra/external-id/cross-tenant-access-overview)
5. Do not apply this human-MFA test to app-only identities. Inspect supported workload controls and effective app permission boundaries instead. [S10: Conditional Access for workload identities](https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)

**Kill criterion:** an applicable path obtains access without the required protection and without a justified, tested exception. **Pass scope:** only the declared population/path coverage and evidence layer. **Consultant criterion.** [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)

## T02 — Emergency access

**Claim to test:** authorized administrators can recover access when ordinary administrative dependencies are unavailable. Microsoft recommends redundant cloud-only emergency accounts, strong independent authentication and recurring validation. [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)

1. Review account independence, permanent active role assignment, authentication methods, policy exclusions, custody and alerts against the live emergency-access guidance. [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)
2. Plan a controlled exercise in which the normal phone or federation path is treated as unavailable. Do not actually disable production identity infrastructure for an audit walkthrough. This non-disruptive exercise design is **consultant method**. [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access); [S65: Entra Connect prerequisites](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/how-to-connect-install-prerequisites)
3. Have an authorized custodian demonstrate credential retrieval and sign-in from the approved secure environment; verify the resulting alert reaches its owner. [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)
4. Record timing, unexpected dependencies, alternate custodian availability and cleanup. Keep credential material out of evidence exports. **Consultant handling method.** [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)

**Kill criterion:** a required dependency is shared with the failed normal path, access fails, or use is not detected. **Closure:** repeat the failed portion after repair and retain new evidence. [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)

## T03 — Historical application consent and least privilege

**Claim to test:** applications can access only approved resources and actions. Changing user-consent settings does not remove existing grants; delegated and application permissions must be assessed separately. [S13: Configure user consent to applications](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)

1. Inventory service principals, delegated grants, app role assignments, owners and credential metadata; identify high-impact access and resource scoping. [S13: Configure user consent to applications](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)
2. Match grants to approval and business need. Review old grants even when new user consent is restricted. [S13: Configure user consent to applications](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent)
3. With a controlled app identity, test an allowed resource/action and a prohibited resource/action. Record status, resource and authentication mode without capturing tokens. **Consultant test design.** [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)
4. Tabletop ownership loss, credential addition and app decommissioning. Confirm incident procedures can revoke malicious access beyond password reset. [S14: App consent grant investigation](https://learn.microsoft.com/en-us/security/operations/incident-response-playbook-app-consent); [S15: Revoke user access in an emergency](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access)

**Kill criterion:** the app can reach an unauthorized resource or no current owner can justify a powerful grant. Record a real test separately from an inference based on broad permissions. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S14: App consent grant investigation](https://learn.microsoft.com/en-us/security/operations/incident-response-playbook-app-consent)

## T04 — Sharing and AI oversharing

**Claim to test:** only the intended business audience can read sensitive content. Sharing configuration, item permissions and discovery restrictions are different controls. [S27: Overview of external sharing in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/external-sharing-overview); [S28: Restrict discovery of SharePoint sites and content](https://learn.microsoft.com/en-us/sharepoint/restricted-content-discovery)

1. Create approved synthetic documents representing sensitive and ordinary information. Record their intended audiences and actual group/direct permissions. **Consultant test design.** [S27: Overview of external sharing in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/external-sharing-overview); [S36: Sensitivity labels](https://learn.microsoft.com/en-us/purview/sensitivity-labels)
2. Test access through a direct URL, existing sharing link and relevant search experience with an owner, authorized recipient, ordinary internal user and external test user. [S27: Overview of external sharing in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/external-sharing-overview); [S28: Restrict discovery of SharePoint sites and content](https://learn.microsoft.com/en-us/sharepoint/restricted-content-discovery)
3. If Copilot is in scope, test representative retrieval prompts and inspect grounding references. Repeat direct access independently; an unsuccessful prompt does not establish a permission boundary. **Consultant interpretation.** [S47: Data, Privacy, and Security for Microsoft Copilot](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-privacy); [S28: Restrict discovery of SharePoint sites and content](https://learn.microsoft.com/en-us/sharepoint/restricted-content-discovery)
4. Check container labels separately from document labels. Confirm how file protection behaves after download or forwarding through supported clients. [S36: Sensitivity labels](https://learn.microsoft.com/en-us/purview/sensitivity-labels)
5. For older Restricted SharePoint Search deployments, inspect the current retirement/migration guidance rather than recommending new enablement unconditionally. [S48: Restricted SharePoint Search](https://learn.microsoft.com/en-us/sharepoint/restricted-sharepoint-search)

**Kill criterion:** an unauthorized persona obtains the synthetic content directly or through a permitted application. **Closure:** repair access, then retest both authorized usability and prohibited access. [S27: Overview of external sharing in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/external-sharing-overview); [S47: Data, Privacy, and Security for Microsoft Copilot](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-privacy)

## T05 — Email authentication, protection and forwarding

**Claim to test:** legitimate senders authenticate and the selected recipient receives intended protection without unauthorized forwarding. [S22: Configure SPF](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-spf-configure); [S23: Configure DKIM](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dkim-configure); [S24: Configure DMARC](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dmarc-configure); [S21: Preset security policies](https://learn.microsoft.com/en-us/defender-office-365/preset-security-policies); [S25: Control external email forwarding](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding)

1. Select one authorized test message from each material sending platform; capture headers and message trace identifiers. Review SPF, DKIM and DMARC alignment for the actual sender domain. [S22: Configure SPF](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-spf-configure); [S23: Configure DKIM](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dkim-configure); [S24: Configure DMARC](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dmarc-configure)
2. Resolve the recipient's effective threat policies. Standard/Strict preset precedence can override a custom policy that looks stronger when viewed in isolation. [S21: Preset security policies](https://learn.microsoft.com/en-us/defender-office-365/preset-security-policies)
3. Inspect forwarding settings, rules, delegates, remote domains and mail-flow exceptions. For an authorized forwarding exercise, use a harmless marker and a controlled destination. **Consultant test design.** [S25: Control external email forwarding](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding); [S87: Get-InboxRule](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/get-inboxrule?view=exchange-ps)
4. Confirm whether the forwarded message is delivered or blocked, and compare with the adopted requirement. Avoid inferring the result solely from “Automatic” forwarding settings. [S25: Control external email forwarding](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding)
5. Review actual SMTP client authentication and mailbox overrides. Check the current retirement timeline; distinguish Basic authentication from SMTP AUTH using OAuth. [S26: Updated SMTP AUTH Basic Authentication deprecation timeline](https://techcommunity.microsoft.com/blog/exchange/updated-exchange-online-smtp-auth-basic-authentication-deprecation-timeline/4489835); [S70: SMTP AUTH configuration](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission)

**Kill criterion:** an unauthorized forwarding path works, an expected protection does not apply, or a legitimate sender fails the adopted authentication target. Mail-flow changes require separate rollout and rollback planning. [S25: Control external email forwarding](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding); [S21: Preset security policies](https://learn.microsoft.com/en-us/defender-office-365/preset-security-policies); [S24: Configure DMARC](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dmarc-configure)

## T06 — Audit event visibility and historical retrieval

**Claim to test:** required events can be investigated over the required history. The Entra activity logs and Purview UAL have different retention and licensing boundaries. [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention); [S18: Manage audit log retention policies](https://learn.microsoft.com/en-us/purview/audit-log-retention-policies)

1. Verify UAL ingestion in an Exchange Online session. Do not interpret the same property from an inappropriate session as authoritative; Microsoft documents this caveat. [S60: Turn auditing on or off](https://learn.microsoft.com/en-us/purview/audit-log-enable-disable)
2. Select a documented audited operation and a known authorized occurrence. Record tenant, actor, object, operation and UTC timestamp. Query a sufficient window after expected ingestion. [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search)
3. Confirm the raw event exists and inspect its essential fields. Compare source and SIEM arrival time if a downstream pipeline is in scope. **Consultant correlation method.** [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention)
4. Retrieve an older known event within the required window for each material user/license/workload stratum. Record source-retention and archive evidence separately. [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention); [S18: Manage audit log retention policies](https://learn.microsoft.com/en-us/purview/audit-log-retention-policies)
5. Reconcile pagination, caps, filters, errors and duplicates before declaring the export complete. For large programmatic acquisition, follow Microsoft's API guidance. [S53: Microsoft Graph paging](https://learn.microsoft.com/en-us/graph/paging); [S56: Search-UnifiedAuditLog](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/search-unifiedauditlog?view=exchange-ps)

**Kill criterion:** the known required event is missing after collection issues are resolved, the required historical period is unavailable, or completeness cannot be established. An authorization error yields Not assessed, not “no suspicious events.” **Consultant decision rule.** [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S56: Search-UnifiedAuditLog](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/search-unifiedauditlog?view=exchange-ps)

## T07 — DLP and classification

**Claim to test:** the policy prevents or detects the specified information transfer for the intended population. DLP capability depends on location and configuration; simulation does not enforce the action. [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp); [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn)

1. Write a scenario: data class, location, actor, destination, expected action and permitted exception. Use a synthetic test pattern with the context needed by the chosen classifier. **Consultant design.** [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp)
2. Include a matching positive specimen and a similar nonmatching negative specimen. Record policy state, rule priority, included locations, assignments and exclusions. [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp); [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn)
3. Test a permitted action and a prohibited transfer on approved clients. Record user experience, block/override behavior and corresponding alert/case. [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp)
4. Review an excluded user or a second location to identify unintended coverage gaps. When enforcement is not enabled, report only what simulation demonstrates. [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp); [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn)
5. Measure false-positive and missed-case observations only within the labeled test set; do not extrapolate a detection rate for all organizational content. **Consultant interpretation.** [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp)

**Kill criterion:** a matching in-scope transfer is allowed contrary to the requirement, or the intended detection never reaches its owner. A useful simulation result supports rollout, not a prevention Pass. [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn); [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp)

## T08 — Device trust and application protection

**Claim to test:** required device/app controls influence actual data access. Intune compliance, access policy and app protection form distinct parts of the design. [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview); [S33: Intune app protection policies](https://learn.microsoft.com/en-us/intune/app-management/protection/overview)

1. Reconcile the test devices with inventory and document platform, enrollment, last check-in, assigned policies and protection state. [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S35: Onboard devices to Defender for Endpoint](https://learn.microsoft.com/en-us/defender-endpoint/configure-machines-onboarding)
2. Test an assigned compliant device, a known noncompliant device, an unassigned device and a relevant grace-period case. Inspect the tenant's no-policy setting and actual access result. [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)
3. On supported BYOD applications, test copy/save to a personal location using synthetic data; verify conditional launch and approved selective-removal behavior. [S33: Intune app protection policies](https://learn.microsoft.com/en-us/intune/app-management/protection/overview)
4. Verify a benign endpoint detection validation produces telemetry and reaches the expected responder. Use the product's approved procedure and a test device; do not introduce malware. **Consultant exercise boundary.** [S35: Onboard devices to Defender for Endpoint](https://learn.microsoft.com/en-us/defender-endpoint/configure-machines-onboarding); [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks)

**Kill criterion:** an intended prohibited device/app path still permits access or transfer, or an expected sensor signal is absent. A device merely appearing in an inventory is insufficient. [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S33: Intune app protection policies](https://learn.microsoft.com/en-us/intune/app-management/protection/overview); [S35: Onboard devices to Defender for Endpoint](https://learn.microsoft.com/en-us/defender-endpoint/configure-machines-onboarding)

## T09 — Recovery and business acceptance

**Claim to test:** a defined recovery unit can be restored within approved RTO/RPO with correct content and access. Legal holds and versioning do not themselves establish a mass-restoration capability. [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide); [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide)

1. Define recovery unit, authorized destination, known-good point, expected content, access permissions, RTO/RPO, start event and acceptance owner before testing. These metrics are **consultant/business definitions**. [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)
2. Verify actual protection coverage and available restore points. Include dependencies such as configuration, credentials and connectors that may fall outside content protection. [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)
3. Restore synthetic or approved test content to an isolated destination where supported. Record declaration time, request time, service completion and business acceptance separately. [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide)
4. Validate readable content, relevant versions, item counts or hashes, permissions and owner acceptance. Calculate observed recovery duration and data age. **Consultant validation method.** [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)
5. Tabletop backup administrator compromise and inspect destructive-change safeguards. Do not delete recovery copies to demonstrate a risk. **Consultant exercise boundary.** [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide)
6. Remove test artifacts only under the approved cleanup plan and retention/hold rules; document whether the tested scale represents a wider recovery claim. [S38: Retention policies and retention labels](https://learn.microsoft.com/en-us/purview/retention); [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide)

**Kill criterion:** missing required data/permissions, unavailable dependencies or recovery beyond the adopted objective. Passing one small restore does not prove tenant-wide ransomware recovery time. [S41: Microsoft 365 Backup overview](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-overview?view=o365-worldwide); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)

2. Test one allowed and one prohibited synthetic data flow. Cover custom or nonblockable connectors in the active policy model; verify existing runtime behavior as well as maker experience. 5. Verify event and incident evidence for the tested action, and repeat after any permission changes. [S47: Data, Privacy, and Security for Microsoft Copilot](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-privacy); [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search)

**Kill criterion:** an out-of-scope action executes, prohibited data crosses the connector boundary, or unapproved model data is publicly accessible. Report exact tested conditions and remaining coverage gaps. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S49: Power Platform data policy strategy](https://learn.microsoft.com/en-us/power-platform/guidance/adoption/dlp-strategy); [S52: Power BI Publish to web](https://learn.microsoft.com/en-us/power-bi/collaborate-share/service-publish-to-web)

## After every test

Preserve observations even when they contradict the initial claim. Clean up approved artifacts, reconcile side effects and attach evidence IDs to the control result. State whether the claim held, was revised or was rejected. This is the playbook's **disconfirmation method**, grounded in the distinction between documented configuration and observed operation throughout the cited Microsoft guidance. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S69: DLP simulation mode](https://learn.microsoft.com/en-us/purview/dlp-simulation-mode-learn); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)
