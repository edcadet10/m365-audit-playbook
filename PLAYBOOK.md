# Microsoft 365 Audit Playbook

**Version 1.0 · Research reviewed 12 October 2026 · Prepared for Jeff Cadet**

A practical methodology for auditing Microsoft 365 security, governance, compliance readiness, resilience and operations. This is an original consultant-authored playbook grounded in Microsoft documentation, supplemented by CISA, CIS, NIST and the maintainers of assessment tools. It is **not a completed tenant audit, a Microsoft-issued standard, or a certification**. No customer tenant was accessed while preparing it.

**How attribution works.** Microsoft links appear beside the procedures and factual statements they inform. A procedure, sample size, priority or acceptance criterion described as **consultant method** is this playbook's proposed audit design, not a claim that Microsoft mandates it. Product documents explain capabilities and limitations; management must adopt the organization's actual requirements. CISA and CIS requirements apply only when adopted or otherwise applicable. [S02: Zero Trust deployment plan with Microsoft 365](https://learn.microsoft.com/en-us/microsoft-365/security/microsoft-365-zero-trust?view=o365-worldwide); [S40: Microsoft Purview Compliance Manager](https://learn.microsoft.com/en-us/purview/compliance-manager); [S62: CISA Entra baseline, ScubaGear v1.8.0](https://raw.githubusercontent.com/cisagov/ScubaGear/v1.8.0/PowerShell/ScubaGear/baselines/aad.md)

## 1. Engagement model

### 1.1 Define the question before collecting settings

**Consultant method.** Ask whether the engagement is a configuration review, an operating-effectiveness audit over a defined period, a readiness assessment against specified requirements, or an investigation. Write the answer in the charter. A configuration export shows state at collection time; it does not establish how consistently a process operated during the prior quarter. Microsoft's audit logs and activity histories can provide additional evidence, subject to their actual coverage and retention. [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention); [S18: Manage audit log retention policies](https://learn.microsoft.com/en-us/purview/audit-log-retention-policies)

Define the business outcomes: resist account takeover; constrain privileged and application access; protect sensitive information; detect abuse; preserve required evidence; restore essential services; and operate the tenant sustainably. Use these outcomes to connect technical observations to business impact, rather than maximizing a dashboard score. Microsoft explicitly limits the assurance that Secure Score provides. [S02: Zero Trust deployment plan with Microsoft 365](https://learn.microsoft.com/en-us/microsoft-365/security/microsoft-365-zero-trust?view=o365-worldwide); [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score)

### 1.2 Establish three evidence layers

| Layer | Audit question | Typical evidence | Microsoft basis |
|---|---|---|---|
| Design | Would the configured control address the adopted requirement? | Policy definitions, scope, license and architecture | [S09: Conditional Access overview](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview); [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp) |
| Implementation | Is it applied to the intended population now? | Assignments, effective permissions, deployment results, exclusions | [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S21: Preset security policies](https://learn.microsoft.com/en-us/defender-office-365/preset-security-policies); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview) |
| Operation | Has it worked in practice during the agreed period? | Sign-ins, alerts, case history, access-review actions, recovery tests | [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S15: Revoke user access in an emergency](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide) |

**Consultant method.** Record a result for each relevant layer. An operating-effectiveness opinion requires operation evidence; do not silently promote a design-only review. A failed known-event search may indicate absent logging, delayed ingestion, incorrect filtering, insufficient permission or exhausted retention. Investigate the cause before concluding that an activity did not occur. [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S60: Turn auditing on or off](https://learn.microsoft.com/en-us/purview/audit-log-enable-disable); [S56: Search-UnifiedAuditLog](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/search-unifiedauditlog?view=exchange-ps)

### 1.3 Adopt a hierarchy for decisions

Use the organization's applicable contract and approved requirements first. For product behavior, use current Microsoft documentation for the actual cloud and feature. Use a dated CISA baseline and a legitimately obtained CIS benchmark as additional criteria. Treat independent tools as evidence generators and cross-checks. Record conflicts, applicability and the reason for selecting a criterion. This hierarchy is **consultant method**, not an assertion that every listed source has regulatory authority. [S45: Microsoft Product Terms](https://www.microsoft.com/licensing/terms/); [S46: Office 365 GCC High and DoD](https://learn.microsoft.com/en-us/office365/servicedescriptions/office-365-platform-service-description/office-365-us-government/gcc-high-and-dod); [S03: ScubaGear](https://github.com/cisagov/ScubaGear); [S05: CIS Microsoft 365 Benchmarks](https://www.cisecurity.org/benchmark/microsoft_365); [S62: CISA Entra baseline, ScubaGear v1.8.0](https://raw.githubusercontent.com/cisagov/ScubaGear/v1.8.0/PowerShell/ScubaGear/baselines/aad.md)

The public CIS catalog was reviewed; the full Microsoft 365 Foundations benchmark was not obtained. This repository does not reproduce the benchmark, invent CIS recommendation identifiers, or claim a complete CIS conformity assessment. If a client requires CIS testing, obtain the applicable version and usage rights, then populate the framework crosswalk. [S05: CIS Microsoft 365 Benchmarks](https://www.cisecurity.org/benchmark/microsoft_365)

### 1.4 Engagement entry and exit gates

**Entry gate — consultant method:** named sponsor and tenant owners; agreed tenants/clouds/workloads; review period; adopted criteria; approved evidence location; access arrangements; exclusions; incident contact; and authorization for any active test. Configuration review and benign testing should have distinct scopes because sign-ins, test messages and restores create tenant activity. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)

**Exit gate — consultant method:** every in-scope control is assessed or explicitly limited; high-risk observations have been communicated through the agreed engagement process; facts are reviewed with owners; remediation and exception decisions have accountable owners; evidence custody is transferred; temporary access is removed; retest criteria are recorded. Closure requires evidence appropriate to the control, not merely a changed setting or closed ticket. [S15: Revoke user access in an emergency](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access); [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S39: eDiscovery features and components](https://learn.microsoft.com/en-us/purview/edisc-features-components)

## 2. Scope and discovery

### 2.1 Inventory the environment

Start with tenant IDs, verified domains, cloud type, subscriptions, identities, devices, enabled services, administrators, integrations, third-party security products and business-critical processes. Reconcile discovery against procurement and acquisition records. Inventory should include users, guests, application identities and partner administration, because Graph permissions and cross-tenant relationships create distinct access paths. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S16: Cross-tenant access overview](https://learn.microsoft.com/en-us/entra/external-id/cross-tenant-access-overview); [S45: Microsoft Product Terms](https://www.microsoft.com/licensing/terms/)

Record data classes and storage locations across email, SharePoint, OneDrive, Teams, analytics, Power Platform, Loop and AI experiences. Follow the actual backing storage; an application interface is not necessarily the storage or compliance boundary. Loop and SharePoint Embedded need explicit attention. [S37: Data loss prevention](https://learn.microsoft.com/en-us/purview/dlp-learn-about-dlp); [S47: Data, Privacy, and Security for Microsoft Copilot](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-privacy); [S77: Loop governance and compliance](https://learn.microsoft.com/en-us/microsoft-365/loop/loop-compliance-summary?view=o365-worldwide); [S84: SharePoint Embedded overview](https://learn.microsoft.com/en-us/sharepoint/dev/embedded/overview)

### 2.3 Discovery interviews

**Consultant interview prompts** should establish requirements and identify evidence, not be accepted as proof of configuration. Interview: executive sponsor on critical outcomes; identity team on privileged paths and emergency access; messaging/collaboration owners on sharing and mail flow; endpoint/SOC teams on coverage and response; records/legal/privacy teams on obligations; application owners on grants and connectors; finance on licenses; business continuity on recovery. Corroborate answers with the corresponding product evidence. [S02: Zero Trust deployment plan with Microsoft 365](https://learn.microsoft.com/en-us/microsoft-365/security/microsoft-365-zero-trust?view=o365-worldwide); [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S38: Retention policies and retention labels](https://learn.microsoft.com/en-us/purview/retention); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)

Ask each owner: what would materially interrupt the business; what information must not leave; which exceptions are essential; what recently changed; which controls are known to be incomplete; and when the last realistic test failed. Record disagreements and missing ownership as work items. These are **consultant prompts**, supported by Microsoft's scenario-driven response and recovery guidance rather than prescribed interview questions. ## 3. Delivery plan and responsibilities

### 3.1 Suggested work plan

The following is a **planning estimate**, not a Microsoft duration or a promised completion time. A single well-documented tenant may fit several weeks; multi-tenant, hybrid or regulated environments can require substantially more time. Confirm effort after discovery. The underlying need to adapt scope follows the different service and cloud capabilities. [S02: Zero Trust deployment plan with Microsoft 365](https://learn.microsoft.com/en-us/microsoft-365/security/microsoft-365-zero-trust?view=o365-worldwide); [S46: Office 365 GCC High and DoD](https://learn.microsoft.com/en-us/office365/servicedescriptions/office-365-platform-service-description/office-365-us-government/gcc-high-and-dod); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)

| Phase | Suggested planning allowance | Deliverables and gate |
|---|---:|---|
| Mobilize | 1–2 working days | Charter, scope, evidence store, contact and access plan |
| Discover and reconcile | 2–4 days | Tenant/workload inventory, license matrix, criteria and sample plan |
| Collect and establish baseline | 2–4 days | Raw evidence, collection manifest, tool output and gap log |
| Validate and challenge | 4–8 days | Manual checks, observed tests, counterexamples and findings |
| Report and agree action | 2–3 days | Executive report, technical register, roadmap and exceptions |
| Retest | Separate agreed window | New evidence against explicit closure criteria |

**Consultant allocation:** schedule recovery, legal and application-owner sessions early; these dependencies often require availability beyond administrators. Preserve enough time for evidence challenges and owner fact checks. Microsoft's recovery and eDiscovery workflows involve steps beyond simple settings review. [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide); [S39: eDiscovery features and components](https://learn.microsoft.com/en-us/purview/edisc-features-components)

## 4. Access and licensing

### 4.1 Use the least access that can produce adequate evidence

Create a named, time-bounded auditor identity using the tenant's required strong authentication. Start with read access, supported delegated scopes and workload-specific reader roles. Where a portal lacks sufficient read-only visibility, prefer an owner-produced export or supervised walkthrough before requesting broader administration. Verify actual authorization per endpoint; Entra roles, Graph scopes and service RBAC are different layers. [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S64: Microsoft Entra built-in roles](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/permissions-reference); [S55: Graph: List Conditional Access policies](https://learn.microsoft.com/en-us/graph/api/conditionalaccessroot-list-policies?view=graph-rest-1.0)

| Evidence area | Starting access approach | Important boundary |
|---|---|---|
| Entra configuration | Security Reader/Global Reader as supported; endpoint-specific Graph read scopes | Listing Conditional Access policies documents Policy.Read.All and supported user roles. [S55: Graph: List Conditional Access policies](https://learn.microsoft.com/en-us/graph/api/conditionalaccessroot-list-policies?view=graph-rest-1.0); [S64: Microsoft Entra built-in roles](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/permissions-reference) |
| Entra activity | Supported activity-log roles/scopes and appropriate entitlement | Retention and available signals differ by license/source. [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview) |

## 8. Risk and prioritization

### 8.1 Assess the scenario, not the setting name

For each finding state: exposed asset, actor or failure scenario, preconditions, reachable population, demonstrated effect, business impact and control dependencies. A weak setting on an unused test service differs from an exploitable administrative path in production. Connect supporting evidence to the specific scenario and avoid claiming a breach from configuration evidence alone. **Consultant risk method.** [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S14: App consent grant investigation](https://learn.microsoft.com/en-us/security/operations/incident-response-playbook-app-consent); [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score)

### 8.2 Suggested rating model

Use ordinal likelihood 1–5 and impact 1–5 with written rationales. Suggested product ranges: 20–25 Critical, 12–19 High, 6–11 Medium, 1–5 Low. Escalate an observed active compromise or confirmed severe exposure through incident procedures regardless of the arithmetic. These thresholds are **consultant choices**, not Microsoft scoring or calibrated probabilities. [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score)

Impact should consider confidentiality, integrity, availability, privacy, contractual exposure and recovery cost. Likelihood should consider reachable access paths, permission scope, actual exposure and tested mitigations. Record inherent and residual assessments separately. Avoid assigning severity solely from a scanner label or Secure Score point value. **Consultant method.** [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview); [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score)

### 8.3 Proposed action priorities

| Priority | Suggested response | Example |
|---|---|---|
| P0 | Triage immediately; agree containment the same day when exposure warrants it | Suspected compromise, uncontrolled admin access, confirmed sensitive public data |
| P1 | Assign owner promptly; target a reviewed near-term plan, often within 30 days | Material coverage gaps, high-risk grants, missing recovery evidence |
| P2 | Schedule a risk-based improvement, often within 60–90 days | Lifecycle, efficiency or lower-exposure governance gaps |

These are **consultant planning defaults**. They are not Microsoft SLAs, legal notification deadlines or permission for disruptive changes. The sponsor adopts deadlines based on business exposure and dependencies. Actual incidents follow the organization's incident authority and Microsoft response guidance. ## 10. Reporting and remediation

### 10.1 Executive report

Lead with the business conclusion for the assessed scope and period, then the most material exposures, uncertainty and decisions required. State what was actually tested. Separate configuration posture, operating evidence and unassessed areas. Include a concise coverage table instead of presenting a single dashboard score as assurance. **Consultant report design.** [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score); [S40: Microsoft Purview Compliance Manager](https://learn.microsoft.com/en-us/purview/compliance-manager); [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search)

Show counts of applicable, assessed, passed, partial, failed and Not assessed controls. If presenting a pass rate, explicitly state its denominator; separately show assessment coverage. Do not hide excluded or untested controls by removing them from the visible population. Changes in license, tool version or scope can make score trends incomparable. **Consultant metric design.** [S01: Microsoft Secure Score](https://learn.microsoft.com/en-us/defender-xdr/microsoft-secure-score); [S57: ScubaGear v1.8.0 output schema](https://raw.githubusercontent.com/cisagov/ScubaGear/v1.8.0/docs/misc/tooloutputschema.md); [S71: Maester 3.0 preview transition](https://maester.dev/blog/maester-3-0/)

Suggested metrics: proportion of privileged paths reviewed; required users with demonstrated access-control coverage; managed/protected endpoint coverage against reconciled inventory; sensitive repositories with approved access; required logs meeting history objectives; critical recovery units with successful timed tests; overdue exceptions; and repeat findings. These are **consultant measures**, with denominators derived from the corresponding Microsoft evidence sources. [S64: Microsoft Entra built-in roles](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/permissions-reference); [S32: Intune device compliance policies](https://learn.microsoft.com/en-us/intune/device-security/compliance/overview); [S27: Overview of external sharing in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/external-sharing-overview); [S17: Microsoft Entra data retention](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-reports-data-retention); [S42: Microsoft 365 Backup FAQ](https://learn.microsoft.com/en-us/microsoft-365/backup/backup-faq?view=o365-worldwide)

### 10.2 Finding record

A defensible finding contains condition, criterion and linked source, evidence IDs, population/sample, cause if established, business consequence, tested counterevidence, severity rationale, owner, proposed action, dependency, deadline and retest condition. Label causal explanations as hypotheses until supported. Distinguish approved exceptions from unexplained failures. **Consultant method.** [S19: Search the audit log](https://learn.microsoft.com/en-us/purview/audit-search); [S43: Incident response playbooks](https://learn.microsoft.com/en-us/security/compass/incident-response-playbooks); [S54: Microsoft Graph permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)

**Synthetic example:** “An MFA policy exists but is in report-only state. For the three synthetic test personas, policy evaluation was recorded without enforcing its grant control. The adopted requirement calls for enforced MFA on those access paths. Scope: the tested resource/client combinations only. Proposed action: correct the policy rollout under change control after reviewing exclusions and recovery access. Closure: export the enforced policy and corroborate allowed/blocked outcomes in new sign-in evidence.” Report-only behavior is documented by Microsoft; the example is not an observation about a real tenant. [S08: Analyze Conditional Access policy impact](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only); [S07: Manage emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)

### 10.3 Remediation roadmap

**Consultant sequencing:** establish reliable emergency access and evidence preservation; address active compromise and exposed privilege; close authentication/application/sharing gaps; validate mail and endpoint protection; implement data governance and recovery improvements; then strengthen lifecycle and continuous monitoring. Dependencies can alter this order—for example, changing authentication before validating emergency access can create a lockout risk. An audit recommendation is not a production change authorization. Changes affecting identity, mail flow, retention, encryption and restores need the organization's normal change process. ### 10.4 Retest and close

**Consultant closure rule:** repeat the original failing scenario, verify the effective scope, check for newly introduced side effects, and inspect new operational evidence.
